## 1 引言

### 1.1 项目概述

本项目为《软件系统设计与应用》课程设计,项目名称为"新生校园知识库与入学事务辅助系统的设计与实现"(2026—2027 学年第 1 学期)。课程要求软件工程与 AI 结合:系统内集成至少一个 AI 组件,体现 AI 特殊需求,并按阶段提交 AI 使用日志。

项目目标(来源:00-project-brief 第 1 节、需求分析说明书 2.0 第 1.2 节):

1. 集中管理新生常用的校园教学、地点、办事、活动信息,减少多渠道查找成本;
2. 支持分类浏览、关键词检索与详情展示,详情包含来源、更新时间、有效期与核实状态,帮助学生判断信息可信度;
3. 提供管理员后台维护能力,支持知识的新增、编辑、审核、上下架与过期信息处理;
4. 集成 AI 问答组件,以知识库检索收敛回答范围,回答附来源、不可信即拒答,降低大模型编造风险。

系统包含两类使用者:学生(浏览、检索、AI 问答)与管理员(登录后维护内容),对应学生端与管理端两个 Web 界面。

### 1.2 设计目标

依据需求分析说明书 2.0 的功能需求(FR-01~FR-13)与非功能需求,本设计阶段确立以下目标:

- **需求可追溯**:每一条功能需求均能双向追溯到接口、页面与测试用例,FR-01~13 全部有接口/页面/测试承载(追溯矩阵见 api-contract.md 第 5 节);
- **接口契约先行**:前后端以唯一契约 `docs/design/api-contract.md` 对接,契约冻结(v1.0,2026-10-24 经用户确认)后任何变更走登记流程,禁止"边写代码边定接口";
- **安全底线**:参数化 SQL、密码哈希、服务端强制鉴权、错误信息不泄露内部细节,四条红线贯穿设计;
- **信息可信**:来源必填、更新时间全链路返回、有效期与核实状态全端同口径展示,未知信息标"待核实",不伪造;
- **AI 合规**:可解释(答案附来源)、鲁棒(多级降级)、公平(不做用户画像)、隐私(仅匿名会话号)。

### 1.3 设计依据

1. 《需求分析说明书 2.0.docx》(需求规格、用户故事 US-01~11、业务模块 M01~M10、主流程 P01~P05、验收用例 TC-01~10);
2. 《软件系统设计与应用》课程设计要求(软件工程 + AI,系统内集成 AI 组件,每阶段提交 AI 使用日志);

### 1.4 设计范围(本期不做项)

本期实现 FR-01~11 与 FR-13(AI 问答,由"扩展"提升为本期必做)。以下功能经需求评审确认**本期不做**,设计文档与实现均未包含(见 00-project-brief 第 1 节;需求符合性审查报告第 6 节确认无超范围实现):

## 2 总体架构设计

### 2.1 架构分层说明

系统采用前后端分离的 B/S 架构:前端为 Vue 3 单页应用(学生端挂 `/`,管理端挂 `/admin`),后端为 Express 分层服务,数据落在 MySQL 8.0,AI 组件由"本地知识库检索器 + DeepSeek 大模型适配器"组成旁路模块。

【图 2-1 总体架构图(此处插入)】

各部分职责(来源:01-system-design 第 1~2 节):

- **前端(frontend,开发端口 5173)**:Vite 开发服务器承载 SPA,生产环境为静态构建产物;所有请求写相对路径 `/api/...`,由 Vite proxy 转发至后端 `http://localhost:3000`,避免跨域与硬编码主机。学生端与管理端共用一套 http 封装(响应包解包、401 清 token 跳登录、403 提示无权限)。
- **后端(backend,端口 3000)**:严格单向分层 `routes → controllers → services → dao → MySQL`,禁止跨层调用(controller 不碰连接池,dao 不判业务权限):
  - routes:声明"路径 → 中间件 → 控制器"装配,挂载 zod 校验、requireAuth/requireRole 鉴权中间件,不写业务逻辑;
  - controllers:解析 query/body(校验在此触发)、调用 service、组装统一响应包,不写 SQL;
  - services:业务规则(如"仅 published 且未过期对学生正常展示""发布前必须审核""published/takedown 编辑保存自动回退 draft")与事务边界;
  - dao:仅参数化 SQL 与行↔对象映射(数据库列 snake_case → 接口字段 camelCase),禁止拼接用户输入。
- **数据库(MySQL 8.0,ssda 库)**:由仓库根 `db/schema.sql`(结构)与 `db/seed.sql`(演示数据)初始化,共 12 张表(详见第 3 章)。
- **AI 模块(services/ai)**:旁路模块,与普通 service 同级,由 AI 对话控制器进入;内部由 KnowledgeRetriever(检索)与 LlmAdapter(生成)两个可替换接口组成(详见第 5 章)。LLM 不可用时在 service 内部降级,不影响其余接口。

### 2.2 技术选型

技术决策已在项目简报中冻结(00-project-brief 第 2 节),变更须经总控裁决:

| 项 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + Vue Router + Pinia + Axios | 学生端/管理端 SPA,组件化复用状态标签、过期横幅 |
| 后端 | Node.js(本地 v24,CI v22,代码兼容 Node 22)+ Express + TypeScript + mysql2 | mysql2 全参数化查询,禁字符串拼接 SQL |
| 参数校验 | zod | 后端入参统一校验,失败返回 400 且 message 含具体字段 |
| 鉴权 | JWT(jsonwebtoken)+ bcryptjs 密码哈希 | token 有效期 12h;管理接口服务端强制校验角色 |
| 数据库 | MySQL 8.0(本机服务 MySQL80) | 初始化脚本 `db/schema.sql` + `db/seed.sql` |
| 测试 | 后端 Jest + ts-jest + Supertest;前端 Vitest + @vue/test-utils | TC-01~10 全部建立自动化映射(docs/testing/tc-mapping.md) |
| AI 生成 | DeepSeek API(`deepseek-chat`,OpenAI 兼容协议) | `DEEPSEEK_API_KEY` 走 .env 不入 git;适配器可切换智谱/通义 |
| AI 检索 | `KnowledgeRetriever` 接口 | 默认 `LocalKbRetriever`(查自建库),预留 `HttpKbRetriever`(外部知识库,仅改配置) |
| 降级策略 | LLM 超时/异常 → 本地检索 + 模板化回答并明确提示 | 检索不到可信内容 → 提示"请核实",禁止编造 |
| 端口 | 后端 3000,前端 5173 | Vite proxy `/api` → `http://localhost:3000` |
| 响应包 | `{ "success": true, "data": ... }` / `{ "success": false, "error": { "code", "message" } }` | 错误不泄露堆栈与凭据 |
| Git | feature 分支开发,阶段完成合并 main,小步上库(Conventional Commits) | 不推远程 |

### 2.3 关键设计决策

1. **响应包统一**:所有接口无一例外返回 `{success, data}` 或 `{success, error:{code, message}}`;`error.message` 为可直接展示给用户的中文;500 统一返回"系统繁忙,请稍后重试",详情仅写服务端日志(TC-10)。唯一例外:`GET /api/admin/ai-logs?export=1` 返回 JSONL 文件流(契约 1.1)。
2. **契约冻结与登记流程**:契约 v1.0 于 2026-10-24 经用户确认冻结;阶段体检发现的 5 个"已实现未登记"端点按"提案 → 总控裁决 → 修订版本号 → 前后端同步"流程补登记为 v1.1(只增不删),保证"先登记再实现"纪律闭环(契约 0 版本记录)。
3. **分层单向调用**:routes→controllers→services→dao 严格单向;AI 模块作为 services 旁路,通过接口(LlmAdapter/KnowledgeRetriever)解耦外部依赖,任一外部服务不可用均不影响主链路可用性(01-system-design 第 2 节)。
4. **先审后发**:知识状态机中,published/takedown 状态的知识经编辑保存后自动回退 draft,必须重新走"提交审核 → 审核通过"才能再次发布,防止未审核内容直达学生端(契约 3.4~3.9)。
5. **权限以服务端为准**:管理端路由守卫仅作体验优化,所有 `/api/admin/*` 接口统一挂 `requireAuth + requireRole('admin')`,前端隐藏入口不算权限控制(TC-07,契约 1.6)。

## 3 数据库设计

### 3.1 概述

数据库为 MySQL 8.0,库名 `ssda`,字符集 utf8mb4(utf8mb4_0900_ai_ci),存储引擎 InnoDB。共 **12 张表**(11 个实体,其中 ai_chat_session 与 ai_chat_message 为 AI 日志组),全部含 `created_at`/`updated_at` 时间戳列;主键 `id` 均 BIGINT UNSIGNED AUTO_INCREMENT;列名 snake_case(仅在 DAO 层出现并就地映射为 camelCase)。建库脚本为 `db/schema.sql`(幂等:DROP+CREATE),演示数据脚本为 `db/seed.sql`(46 条知识覆盖四态与已过期样例)。

### 3.2 表清单与逐表说明

(来源:db/schema.sql;用途标注对应业务模块 M01~M10)

**表 1 admin_user(管理员账号表,M08)**:存储后台登录账号。关键字段:`username`(登录名,唯一,3~30 字符,UNIQUE KEY uk_admin_username)、`password_hash`(bcryptjs 哈希,禁存明文)、`role`(固定 admin,为 requireRole 预留)、`last_login_at`(最近登录时间)。

**表 2 knowledge_category(知识分类表,M01)**:知识分类字典。关键字段:`name`(分类名,唯一,1~50 字,UNIQUE KEY uk_category_name)、`description`(≤200 字)、`sort_order`(排序值,越小越靠前,索引 idx_category_sort)、`is_enabled`(1 启用 0 停用;学生端接口仅返回启用分类)。

**表 3 knowledge(校园知识表,M02/M09/M10,核心表)**:校园知识条目。关键字段:`category_id`(外键 → knowledge_category.id)、`title`(1~100 字必填)、`content`(正文必填)、`source`(信息来源必填,FR-11)、`status`(ENUM:draft/pending_review/published/takedown,默认 draft)、`is_verified`(1 已核实 0 待核实,FR-10)、`effective_from`(有效期起,必填 DATE)、`effective_until`(有效期止,可空表示长期有效)。约束:外键 fk_knowledge_category;CHECK 约束 chk_knowledge_validity(`effective_until IS NULL OR effective_until >= effective_from`)。

**表 4 knowledge_change_log(知识变更日志表,M10)**:管理端写操作审计。关键字段:`knowledge_id`(外键 → knowledge.id,**ON DELETE CASCADE**)、`admin_id`(操作人,外键 → admin_user.id)、`action`(create/update/delete/submit_review/review_publish/review_reject/takedown 七类)、`detail`(变更摘要或驳回原因)。索引 idx_change_log_knowledge(knowledge_id, created_at)。

**表 5 location(校园地点表,M05)**:被办事指南、活动、教师办公室、任教关系引用的公共地点表。关键字段:`name`(1~100 字必填)、`campus`(校区,必填)、`building`/`floor`/`room`(建筑/楼层/房间)、`description`(≤500 字)。

**表 6 service_guide(办事指南表,M03)**:校园卡补办、水卡、宿舍报修、网络故障等办事事项。关键字段:`title`(必填)、`department`(办理部门,1~100 字必填)、`location_id`(办理地点,外键 → location.id,可空)、`service_time`(办理时间)、`materials`(所需材料)、`process`(办理流程)、`is_enabled`(1 上架 0 下架)。

**表 7 campus_activity(校园活动表,M04)**:校园跑、太极拳等活动。关键字段:`title`(必填)、`start_time`/`end_time`(DATETIME,必填)、`location_id`(活动地点,可空)、`signup_method`(报名方式 ≤200 字)、`target_audience`(适用对象 ≤200 字)、`description`、`is_enabled`。约束:CHECK 约束 chk_activity_time(`end_time >= start_time`)。

**表 8 teacher(教师表,M06)**:仅存允许公开字段(姓名/职称/办公室/答疑时间),**不设**电话、工号等隐私列(隐私红线)。关键字段:`name`(1~50 字必填)、`title`(职称 ≤50 字)、`office_location_id`(办公室,外键 → location.id,可空)、`office_hours`(答疑时间 ≤100 字)。

**表 9 course(课程表,M06)**:关键字段:`name`(课程名必填)、`code`(课程代码,唯一,UNIQUE KEY uk_course_code)、`semester`(开课学期,如 2026-2027-1)、`description`(≤500 字)。

**表 10 course_teacher(任教关系表,M06)**:课程×教师多对多关系,含上课教室与时间。关键字段:`course_id`/`teacher_id`(双外键)、`location_id`(上课教室,可空)、`schedule`(上课时间 ≤100 字)。约束:UNIQUE KEY uk_course_teacher(course_id, teacher_id) 防止重复关联(重复时业务层返回 409)。

**表 11 ai_chat_session(AI 对话会话表,FR-13 日志)**:关键字段仅 `session_key`(匿名 uuid,36 位,UNIQUE KEY uk_session_key)。**全表无任何身份关联列**——这是 AI 隐私红线的落库体现。

**表 12 ai_chat_message(AI 对话消息表,FR-13 日志)**:关键字段:`session_id`(外键 → ai_chat_session.id,ON DELETE CASCADE)、`role`(ENUM:user/assistant)、`content`(消息正文)、`sources_json`(JSON,引用来源数组,assistant 专有)、`mode`(生成模式:deepseek/fallback,assistant 专有)、`retriever`(检索器:local_kb,预留 http_kb)、`latency_ms`(检索+生成总耗时)。索引:idx_message_session(session_id, created_at)、idx_message_created(created_at)(管理端按时间筛选)。

### 3.3 主外键与索引设计

外键关系共 10 条(来源:schema.sql):knowledge.category_id → knowledge_category.id;knowledge_change_log.knowledge_id → knowledge.id(级联删除)、admin_id → admin_user.id;service_guide.location_id、campus_activity.location_id、teacher.office_location_id、course_teacher.location_id → location.id;course_teacher.course_id → course.id、teacher_id → teacher.id;ai_chat_message.session_id → ai_chat_session.id(级联删除)。

索引按"支撑 2 秒查询口径"设计(01-system-design 第 6 节、审计报告 3.8 节核对通过):

- **前缀索引**:`knowledge.title` 全列索引(idx_knowledge_title)、`knowledge.content(100)` 前 100 字符前缀索引(idx_knowledge_content)——正文为 TEXT 类型,前缀索引兼顾 LIKE 检索与索引体积;各业务表 title 列均建索引。
- **组合索引**:`knowledge(category_id, status)` 支撑"分类+状态"列表查询;`knowledge(status, effective_until)` 支撑过期工作台按状态与有效期筛选;`location(campus, name)` 支撑校区+名称排序检索;`service_guide(is_enabled, updated_at)`、`campus_activity(is_enabled, start_time)` 支撑上架内容按时间排序;`knowledge_change_log(knowledge_id, created_at)`、`ai_chat_message(session_id, created_at)` 支撑日志按时间线读取。
- **唯一约束**:admin_user.username、knowledge_category.name、course.code、course_teacher(course_id, teacher_id)、ai_chat_session.session_key。
- 排序列全部为硬编码白名单,ORDER BY 不接受外部输入(防注入,审计 3.1 节)。

### 3.4 知识状态机

`knowledge.status` 四态:**draft(草稿)→ pending_review(待审核)→ published(已发布)↔ takedown(已下架)**,流转规则与契约 3.4~3.9 一致(先审后发):

1. 新增知识初始为 draft;仅 draft 可物理删除,其余状态删除返回 409(引导走下架);
2. draft(或 takedown)经"提交审核"进入 pending_review;重复提审返回 409;
3. 审核通过(publish)进入 published;驳回(reject,comment 必填)回到 draft;
4. published 可下架进入 takedown,takedown 可重新提审;
5. **published/takedown 编辑保存后自动回退 draft**(先审后发红线),防止未审核内容直达学生端;
6. 学生端可见性:仅 `published` 出现在列表与详情;其中 `effective_until < 今天` 的仍可见但服务端计算 `isExpired=true`(前端渲染过期横幅,TC-09);`takedown`(及 draft/pending_review)对学生端不可见,详情请求返回 404;
7. 每次状态流转写入 knowledge_change_log(七类 action),全操作可追溯。

## 4 接口设计

### 4.1 统一响应包

(来源:api-contract.md 1.1,冻结)

```json
// 成功(所有接口,无一例外)
{ "success": true, "data": { } }
// 失败
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "标题不能为空" } }
```

- `error.code` 为大写蛇形;`error.message` 为可直接展示给用户的中文;
- 失败响应不得包含堆栈、SQL、连接串、密钥;500 统一返回"系统繁忙,请稍后重试",详情仅写服务端日志(TC-10);
- 唯一例外:`GET /api/admin/ai-logs?export=1` 返回 JSONL 文件流。

### 4.2 错误码表

| HTTP | code | 语义 | 典型场景 |
|---|---|---|---|
| 400 | VALIDATION_ERROR | 参数错误,message 含具体字段 | 缺标题、日期格式非法(TC-08)、空关键词 |
| 401 | UNAUTHORIZED | 未登录 / token 缺失或无效 | 管理接口未带 token、登录密码错误(TC-07) |
| 403 | FORBIDDEN | 已登录但角色未授权 | 非管理员角色调管理接口(TC-07) |
| 404 | NOT_FOUND | 资源不存在 | 学生端访问已下架知识("知识不存在或未发布") |
| 409 | CONFLICT | 业务状态冲突 | 删除仍有关联知识的分类;删除非草稿知识;重复任教关系 |
| 500 | INTERNAL_ERROR | 服务器异常,统一"系统繁忙,请稍后重试" | 数据库不可用(TC-10) |

### 4.3 分页规范

- 请求:`page`(从 1 开始,默认 1)、`pageSize`(默认 10,上限 100);
- 响应:`data = { list, total, page, pageSize }`;

## 5 AI 组件设计

### 5.1 总体链路

AI 组件对应 FR-13,由"检索收敛 + 大模型生成 + 多级兜底"构成(来源:02-ai-component-design):

【图 5-1 AI 对话总体链路图(此处插入)】

链路步骤:用户提问(POST /api/ai/chat,sessionId=uuid、message 1~500 字)→ zod 校验 → KnowledgeRetriever 检索已发布内容 → 按相关度排序收敛取 top-K(默认 5)→ 可信判定 → 有可信内容则组装提示词调用 DeepSeek 生成(回答要求引用 [1][2] 编号),无可信内容则**不调 LLM**、直接返回核实话术("知识库未覆盖该问题,请咨询相关部门核实",sources=[],禁止编造)→ 会话与消息落库(ai_chat_session/ai_chat_message,含 sources_json/mode/retriever/latency_ms)→ 返回 200 响应,前端渲染回答、来源列表与降级提示。

### 5.2 LocalKbRetriever v1.1 检索算法

检索器实现 `KnowledgeRetriever` 接口(方法签名 `retrieve(question): Promise<RetrieverResult>`,返回 items/isReliable/retriever),默认实现 LocalKbRetriever 查询自建库(代码位于 `backend/src/ai/retriever/`):

- **数据范围**:仅已发布/上架内容——knowledge(status='published')、service_guide(is_enabled=1)、campus_activity(is_enabled=1)、course、teacher、location 六类;已下架/草稿/待审核一律检索不到;过期知识可被检索但在 snippet 中带"(已过期)"标注。
- **分词(v1.1 修订)**:对问题先保整句(2~8 字问句整句作为 strongTerm,命中 ×2 加权);≥3 字分段再切**步长 1 的重叠 2-gram**(修复了初版步长 2 切分丢失词边界、导致恰为 8 字短问句整体无命中而误拒答的缺陷,见审计 A-05 与 AI 质量报告)。
- **打分公式**:(标题命中 ×3 + 摘要命中 ×1,整句命中 ×2)×(1 + 查询词覆盖率)+ 已核实 ×1 + 在有效期内 ×1;按 score 降序取 top-5;最高分低于阈值(默认 1)时 isReliable=false。覆盖率权重用于抑制高频 2-gram 的排序噪声,保证命中查询中不同关键词的条目优先。
- **实现约束**:六表并行 `title LIKE CONCAT('%', ?, '%')` 优先、描述字段次之,全部参数化;每条结果标注来源字段(source/department 等)与 updatedAt,供前端展示与 sources_json 落库。

预留实现 HttpKbRetriever:通过环境变量 `KB_API_BASE_URL` 配置外部知识库地址(POST {baseUrl}/retrieve,超时 5s,失败按"检索无结果"处理不影响主流程),实现同一接口后由工厂按环境变量选择,**不改动 service 其余代码**(对应简报"仅改配置"的决策)。

### 5.3 DeepSeek 适配器

适配器实现 `LlmAdapter` 接口(`chatCompletion(system, user): Promise<LlmResult>`,失败抛 LlmError),代码位于 `backend/src/ai/llm/deepseek-adapter.ts`,经 OpenAI 兼容协议调用 `{DEEPSEEK_BASE_URL|https://api.deepseek.com}/chat/completions`。生成参数(02 设计 3.2 节):

| 参数 | 值 | 说明 |
|---|---|---|
| model | deepseek-chat | OpenAI 兼容协议 |
| temperature | 0.3 | 偏保守,减少编造倾向 |
| max_tokens | 600 | 覆盖 300 字回答 + 来源列表 |
| timeout | 20s(AbortController) | 超时即降级 |
| stream | false | 一次性返回,便于落库与耗时统计 |

可替换性:实现同一 LlmAdapter 接口即可切换智谱/通义;工厂按 `LLM_PROVIDER` 环境变量选择,默认 deepseek;`DEEPSEEK_API_KEY` 未配置时工厂返回 NullLlmAdapter(调用即抛 LlmUnavailable),service 捕获后走降级。Key 只放 `backend/.env`,不入 git、不出现在日志与提示词存档。

### 5.4 三级兜底设计

降级判定优先级(02 设计第 1 节):

1. **检索无可信内容** → 无论 LLM 可用与否,不调 LLM,返回固定核实话术 + sources=[](禁止编造);
2. **DEEPSEEK_API_KEY 未配置** → 直接走模板化回答(mode=fallback),不发起 HTTP;降级模板固定首行注明"当前为降级模式,回答由本地检索结果直接整理,请以官方通知为准";
3. **已配置但超时(20s)/网络错误/HTTP 非 2xx/返回空** → 同样降级为模板化回答,并记录错误日志。

辅助兜底:user 消息在检索前落库(即使后续异常也有输入记录);assistant 消息落库失败不阻塞响应、记 error 日志(对话可用性优先);输入长度 1~500 字由 zod 拦截;外部检索器失败不影响主流程。`mode` 字段如实记录 deepseek/fallback,供管理端统计降级率(鲁棒性证据)。

### 5.5 提示词 v1 与注入防线

系统提示词 v1 存档于 `docs/ai-logs/prompts/ai-chat-system-prompt-v1.md`(改动语义必须新版本文件 + dev-usage-log 台账登记,禁原地改写),核心约束:只依据"资料"部分回答、资料外一律不编造;回答末尾列引用来源编号([1] 条目标题(来源:xxx,更新于日期));资料不足或矛盾时回答"知识库未覆盖该问题,请咨询相关部门核实";易变信息提醒以最新通知为准;不收集、不询问、不记录个人身份信息;不回答与校园生活/办事/教学无关的问题;简体中文、不超过 300 字、步骤类问题用编号列表。

**注入防线**:用户输入只进 user message,禁止拼入 system prompt(提示词中 `{sources_block}` 仅由服务端从检索结果渲染,不含任何用户历史消息);user message 原文透传不做模板包裹;长度 500 上限在 zod 层拦截。实测验证(功能测试报告 AI-06):注入攻击下不泄露系统提示词、密钥与连接串。

### 5.6 合规四性(课程硬性要求)

| 要求 | 设计落地 | 证据/验证 |
|---|---|---|
| 可解释 | 回答附来源编号列表;sources[] 随响应返回并渲染可点击来源;mode/retriever 如实标注;管理员可在 /admin/ai-logs 逐条审计 | 契约 2.15;ai_chat_message.sources_json;AI 专项用例 |

## 7 安全与非功能设计

(来源:01-system-design 第 6 节、00-project-brief 3.5、docs/audits/code-audit-report.md 审计结论)

### 7.1 安全设计

1. **参数化 SQL(防注入,P0 红线)**:全库用户输入一律走 `?` 占位符;模糊查询统一 `LIKE CONCAT('%', ?, '%')`(通配符位于参数位);ORDER BY 列名全部硬编码白名单;LIMIT/OFFSET 参数化;审计逐项核对通过(审计 3.1 节)。
2. **密码安全**:bcryptjs 哈希存储与校验(cost 10),无明文/MD5;登录响应仅返回 token 与 id/username/role,不回哈希;401 话术统一"用户名或密码错误",不区分账号存在性(审计 3.3 节)。seed 预置管理员 admin/admin123 仅限课程演示,README 已注明"演示或部署前请修改密码与 JWT_SECRET"。
3. **鉴权与 CORS**:JWT 签发(payload 含 adminId/username/role,有效期 12h),`/api/admin/*` 统一挂 requireAuth+requireRole;**JWT_SECRET 必填**(缺失或短于 16 位服务拒绝启动,fail-fast,修复审计 A-01);CORS 收敛为 origin 白名单(默认 http://localhost:5173,环境变量可配,修复审计 A-02)。
4. **入参校验**:zod 覆盖全部写接口(body/query/params),strict 模式拒绝多余字段(实测 phone → 400);统一 validate 中间件挂载于路由层,校验失败返回 400 且 message 为中文并指明字段(修复审计 A-06 的英文报错偏差)。
5. **错误信息不泄内部细节**:500 统一"系统繁忙,请稍后重试",堆栈仅写服务端日志;实测全部 4xx/5xx 响应无 stack/SQL/连接串/主机端口(TC-10,审计 3.4 节)。
6. **XSS 防线**:全前端无 v-html/innerHTML/eval;AI 回答、知识正文、搜索词均走文本插值;无动态 javascript: 链接(审计 3.6 节)。
7. **AI 提示词注入防线**:用户输入仅作为 user message 透传,system prompt 为固定约束 + 检索资料,无用户输入拼接面(审计 3.7 节)。
8. **敏感配置**:`.env` 不入 git(.gitignore 覆盖,git ls-files 核查仅 .env.example 被跟踪);DEEPSEEK_API_KEY、DB 密码、JWT_SECRET 全部出自环境变量,日志不打印 token 全文与 Key。
9. **真实日历日期校验**:知识/活动/AI 日志的日期字段在服务端校验真实日历合法性(如 2026-13-99、2026-02-30 拒绝并提示"日期不合法,请选择真实存在的日期"),前端日期指令双保险拦截手输非法值(GUI 验收 D-MED-2 修复,+5 条后端测试)。
10. **隐私最小化**:teacher 表不设电话/工号等隐私列;AI 仅匿名 uuid 会话;导出文件不入 git。

### 7.2 性能设计(普通查询 2 秒口径)

- 连接池复用;列表查询只取展示列;
- 索引支撑:knowledge 标题/正文前缀索引、(category_id,status) 与 (status,effective_until) 组合索引、location(campus,name) 等详见 3.3 节;
- 聚合搜索六类资源并行查询;请求耗时中间件记录 latency_ms(AI 链路落库 latency_ms 观测"2 秒口径")。

### 7.3 可靠性、兼容性与可维护性

- **可靠性**:数据库异常友好提示不暴露堆栈;/api/health 降级探测(db:down 仍返回 200 供运维判断);AI 落库失败不阻塞对话响应。
- **兼容性**:Chrome/Edge 最新两个大版本;代码兼容 Node 22(本地 v24 开发,CI v22)。
- **可维护性**:前后端分层、命名一致(接口 camelCase/数据库 snake_case);提供数据库初始化脚本;管理端写操作一律落 knowledge_change_log 可追溯;来源与 updatedAt 全链路返回并展示(FR-11)。

## 8 部署设计

### 8.1 数据库初始化

使用仓库根 `db/schema.sql` 与 `db/seed.sql`(README 快速启动口径):

```bash
mysql -u root -p < db/schema.sql   # 建库 ssda + 12 张表(幂等,可重复执行)
mysql -u root -p < db/seed.sql     # 灌入演示数据(6 分类/46 知识覆盖五态/14 地点/11 教师/9 课程+12 任教关系/10 指南/8 活动/变更日志样例)
```

注意:schema 会覆盖已有同名库数据;seed 中管理员口令仅限演示环境。

### 8.2 环境配置(.env)

后端配置文件 `backend/.env`(不入 git,模板见 `backend/.env.example`):

| 配置项 | 说明 |
|---|---|
| PORT / NODE_ENV | 服务端口(默认 3000)与运行环境 |
| DB_HOST / DB_PORT / DB_USER / DB_PASSWORD / DB_NAME | MySQL 8.0 连接信息(默认库 ssda) |
| JWT_SECRET | **必填**,≥16 字符,缺失或过短服务拒绝启动 |
| JWT_EXPIRES_IN | token 有效期(默认 12h) |
| CORS_ORIGIN | CORS 白名单,逗号分隔,默认 http://localhost:5173 |
| DEEPSEEK_API_KEY | DeepSeek 密钥;未配置时 AI 对话自动降级为本地检索模板回答 |
| DEEPSEEK_BASE_URL / DEEPSEEK_MODEL | 默认 https://api.deepseek.com 与 deepseek-chat |
| LLM_TIMEOUT_MS | LLM 超时(默认 20000ms,超时降级) |
| KB_API_BASE_URL | 外部知识库地址(可选;不配置时使用本地检索器) |

### 8.3 快速启动步骤

前提:MySQL 8.0 与 Node.js 22+。步骤(README):

1. 执行 8.1 节两条命令初始化数据库;
2. 启动后端:`cd backend && cp .env.example .env`(修改 DB_PASSWORD 与 JWT_SECRET)→ `npm install` → `npm run dev`(端口 3000);
3. 启动前端:`cd frontend && npm install` → `npm run dev`(端口 5173,已配置 /api 代理到 3000);
4. 访问学生端 http://localhost:5173/ 与管理端 http://localhost:5173/admin/login;AI 问答可选:在 backend/.env 填入 DEEPSEEK_API_KEY 后重启后端即切换为模型生成,未配置自动走本地检索降级模式。

### 8.4 CI 流水线概述

`.github/workflows/ci.yml` 为三 job 结构(触发:push/PR 到 main + 手动;同 ref 新运行取消旧运行)(来源:worklog-ci 与 ci.yml):

1. **course-materials(课程材料检查)**:校验课程要求材料存在;
2. **frontend**:Node 22 + npm 缓存 → npm ci / lint / test(Vitest)/ build(vue-tsc + vite),构建产物 dist/ 上传 artifact(保留 7 天);
3. **backend**:Node 22 + mysql:8.0 service container(root/root,预建 ssda_test 库,utf8mb4,mysqladmin ping 健康检查)→ job 级预置 DB_*/JWT_SECRET/NODE_ENV/CORS_ORIGIN 环境变量 → npm ci / lint / test(Jest,globalSetup 自动向 ssda_test 执行 db/schema.sql)/ build。

总控曾按 CI 同款环境变量在本机删除 ssda_test 库模拟全新 runner 实测:15 套件用例全绿(总控工作日志 2026-10-24 21:30)。首次 push 后需到 GitHub Actions 确认三 job 全绿(由用户决定 push 时机)。

# SSDA 监控方案

- 项目:新生校园知识库与入学事务辅助系统(SSDA)
- 日期:2026-10-25(对应仓库当前实现)
- 口径说明:本方案只描述**当前已实现**的监控机制;第 4 节为演进项,均已标注「未实现,规划」,不作为现有能力引用。

## 1. 监控目标与口径

| 目标 | 口径 | 依据 |
| --- | --- | --- |
| 可用性 | 后端进程存活 + MySQL 连通,以 `GET /api/health` 返回的 `db:"up"/"down"` 判定 | 契约 2.1,TC-10 辅助 |
| 性能 | 普通查询(学生端列表/详情/检索类接口)目标 **2 秒内返回**;AI 对话耗时以 `ai_chat_message.latency_ms`(检索+生成总耗时,毫秒)记录 | 需求书 NFR:「普通查询 2 秒内返回」 |
| AI 降级率 | assistant 消息按 `mode`(deepseek / fallback)落库,降级率 = fallback 条数占总条数比例;降级是预期行为(未配 Key、超时、异常均回落),回答首行固定声明降级模式,对用户可解释 | 设计文档 02 第 4/6 节 |
| 错误安全 | 未知错误由统一错误处理捕获,客户端仅收到 500「系统繁忙,请稍后重试」,不泄露堆栈与连接凭据;错误详情只进服务端日志 | 错误中间件注释,TC-10 |

## 2. 已实现监控点

### 2.1 健康检查 GET /api/health(无鉴权)

- 探测方式:对数据库执行 `SELECT 1`;成功返回 `db:"up"`,失败返回 `db:"down"`。
- 响应包:`{"success":true,"data":{"status":"ok","db":"up"|"down","time":"…"}}`;数据库不可用时**仍返回 HTTP 200**,以 `db` 字段区分,便于脚本只看响应体即可判定,且不向外暴露内部错误细节。
- 可直接以浏览器、curl 或巡检脚本调用,是当前唯一的进程级探活入口。

### 2.2 请求日志(morgan)

- `NODE_ENV ≠ test` 时启用 `morgan('dev')`,控制台输出每条请求的方法、路径、状态码与响应耗时;test 环境自动关闭,避免干扰测试输出。
- 该日志仅记录请求行,不含请求头与请求体,因此 JWT token、请求参数与密码不会进入访问日志。

### 2.3 统一错误日志与安全响应

- 业务可预期错误(HttpError)按状态码 + code + message 返回;zod 参数校验错误统一转 400;未知错误记录 `console.error('[unhandled]', err)` 后向客户端返回统一 500 提示。
- 日志卫生:现有全部日志路径(morgan 请求行、错误对象、AI 降级原因摘要)均不输出密码、JWT token 与 DEEPSEEK_API_KEY;AI 的 system prompt 也不含用户原始输入与任何密钥。

### 2.4 AI 对话指标落库(ai_chat_message)

- assistant 消息记录 `mode`(deepseek / fallback)、`retriever`、`latency_ms`、`sources_json`;user 消息在检索前先落库,链路异常时也有输入记录可查。
- assistant 消息落库失败不阻塞回答返回,仅记 error 日志,对话可用性优先,可由导出脚本兜底补录。
- 管理端 `GET /api/admin/ai-logs` 支持按 sessionKey、起止日期分页查询,列表字段含 `mode`、`retriever`、`latencyMs`,可用于逐条核查降级原因与单次对话耗时(契约 3.19)。

### 2.5 对话日志导出统计(npm run export:ai-logs)

- 读取 `ai_chat_session` + `ai_chat_message` 全量,输出 JSONL 至 `docs/ai-logs/exports/`(该目录不入 git,提交材料前需重新导出)。
- 控制台同步输出三项统计:总条数、fallback(降级)条数、降级率百分比(实测样例:「已导出 12 条消息……fallback(降级)条数:6,降级率:50.0%」),作为阶段汇报中鲁棒性与可解释性的量化证据。

## 3. 演示前巡检清单

按序执行,任一步异常先排障(参照《部署文档》第 7 节)再开始演示:

1. 访问 `GET http://localhost:3000/api/health`,确认返回 `db:"up"`;
2. 打开学生端 `http://localhost:5173/`,确认知识库、课程等演示数据可见;
3. 进入 `http://localhost:5173/admin/login`,用管理员账号登录成功;
4. AI 对话发起一轮:命中条目时返回带来源编号的回答,`mode` 与当前 Key 配置一致(未配 Key 时应为 fallback,且回答首行声明降级);
5. 执行 `npm run export:ai-logs`,确认导出成功且总条数、降级率统计输出正常。

## 4. 演进项(未实现,规划)

以下能力当前版本**未实现**,列为后续演进方向:

1. **uptime 外部探活**:由外部拨测服务(UptimeRobot 等)周期请求 `/api/health` 并在异常时告警;当前仅支持人工或脚本探测。
2. **慢查询日志**:开启 MySQL `slow_query_log`,对超过阈值(如 2 秒)的 SQL 用 EXPLAIN 分析优化;当前未开启。
3. **前端错误上报**:收集 `window.onerror` / Promise rejection 并上报后端;当前前端异常仅停留在浏览器控制台。
4. **可视化面板**:基于 `ai_chat_message` 聚合降级率与平均 latency 趋势的 Grafana 类面板;当前以管理端日志查询与导出统计替代。

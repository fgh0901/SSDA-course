# ssda-requirements:需求与设计文档规范

目标读者:从未参与本项目的开发者/子 Agent。读完本文件,你应能按项目统一口径产出需求与设计文档,不引入与既有文档冲突的编号、措辞或路径。

## 1. 什么时候必须用本 skill

- 梳理、编写、修改需求条目(FR/US)、用户故事、验收标准
- 产出各 Phase 设计文档:ER 图、数据库 DDL、页面设计、流程图
- 建立/维护需求追溯矩阵
- 回答"这个编号是什么意思""这个需求做到什么程度算验收通过"

API 契约相关走 `ssda-api-contract`;代码走 `ssda-backend`/`ssda-frontend`;测试走 `ssda-testing`。

## 2. 事实来源与冲突处理(先读这一节)

优先级从高到低:

1. `需求分析说明书2.0.docx`(项目根目录,需求最高依据)
2. `docs/design/00-项目简报.md`(全体 Agent 的统一事实来源)
3. 其他设计文档

发现文档之间冲突:一律不得自行修改简报或 docx,在完成报告/工作日志中上报总控裁决。

## 4. 追溯矩阵写法(设计 → FR → TC 双向)

矩阵**内嵌在 `docs/design/接口契约.md` 第 5 节**(总控裁决 2026-10-24:契约内嵌为准,保证与接口定义同步更新,不另建独立文件;如未来需要独立需求文档再抽取)。

**正向**(设计文档里写):每个设计产物必须标明覆盖的 FR 与验证它的 TC。

| 设计产物 | 覆盖 FR | 涉及模块 | 涉及表/接口/页面 | 验证 TC |
|---|---|---|---|---|
| 知识列表页 | FR-01、FR-02、FR-10 | M01/M02/M07 | GET /api/knowledge | TC-01、TC-02、TC-03、TC-05、TC-09 |
| 管理员新增知识表单 | FR-08、FR-11 | M09 | POST /api/admin/knowledge | TC-06、TC-08 |

**反向**(测试覆盖检查时写):每个 TC 标明来源 FR;每个"高"优先级 FR 必须至少被一个 TC 覆盖,否则视为设计缺口,上报总控。

| TC | 操作 | 预期 | 来源 FR |
|---|---|---|---|
| TC-09 | 查看已过期知识 | 显示过期标识或隐藏已下架内容 | FR-10 |

## 5. 验收标准措辞

- **可验证、可量化**:写"普通查询 2 秒内返回"(简报 3.5 的验收口径),不写"响应要快"。
- 用 Given / When / Then 三段式:
  - Given:学生处于知识列表页,且数据库中存在已发布(published)知识
  - When:输入关键词"校园卡"并搜索
  - Then:列表仅返回标题或正文命中的记录,且每条展示标题、分类摘要
- 禁用模糊词:"等等""酌情""尽量""合理地"。确需主观判断(如"友好提示"),必须给出判据(如"不出现堆栈与数据库凭据")。
- 每条 FR 至少一个 TC 覆盖,或显式标注"本期不做"(如 FR-12)。
- 措辞反例对照:

| 反例(禁止) | 正例(推荐) |
|---|---|
| 响应要快 | 普通查询 2 秒内返回(简报 3.5 口径) |
| 报错要友好 | 数据库异常时返回统一"系统繁忙"话术,响应不含堆栈与凭据 |
| 不合法输入要拦截 | 缺标题或日期格式非法时拒绝保存,提示含字段名的具体错误(TC-08) |
| 管理功能要有权限 | 管理接口未携带有效 token 返回 401,角色不符返回 403(TC-07) |

## 6. 文档产出模板与存放路径

```text
docs/
├── design/
│   ├── 00-项目简报.md      # 已存在,勿改
│   ├── 接口契约.md          # 契约,由总控冻结/修订;追溯矩阵内嵌于第 5 节
│   └── NN-<主题>.md             # 其他设计文档:两位序号 + kebab-case
├── worklogs/                    # 各 Agent 工作日志(worklog-<agent>.md)
└── ai-logs/                     # AI 使用日志,见 ssda-ai-log
```

新建设计文档前先查看 `docs/design/` 现有序号,避免撞号;文档命名用小写 kebab-case,如 `01-er-diagram.md`。

### 需求条目卡模板(设计文档中引用某条 FR 时使用)

```markdown
### FR-10 知识状态与有效期
- 优先级:高
- 描述:知识具备状态(draft / pending_review / published / takedown)与
  有效期(effective_from / effective_until),过期或待核实信息对学生端有明显提示。
- 验收标准:
  - Given 数据库中存在 effective_until 早于当前时间的已发布知识
  - When 学生打开该知识详情
  - Then 页面顶部展示过期横幅,且响应中 status 字段原样返回
- 涉及表:knowledge
- 涉及接口:GET /api/knowledge/:id、GET /api/admin/knowledge/expired
- 验证用例:TC-09
```

## 7. Do / Don't

**Do**

- 写任何需求/设计文档前,先完整读简报与需求分析说明书相关章节
- 引用一律带编号("FR-08""TC-09"),不写"知识管理相关需求"
- 设计文档末尾附"追溯矩阵"小节
- 保持既有编号稳定;确需增删改,在完成报告中提请总控

**Don't**

- 禁止私自新增、删除、重排 FR/US/M/P/TC 编号
- 禁止修改简报、需求分析说明书 docx、接口契约.md(仅总控有权)
- 禁止在验收标准里写无法执行检验的措辞
- 禁止绕过编号体系自创"需求 1.1.3"式编号

## 8. 协作约束

完成任务过程中,按项目规范维护 `docs/worklogs/worklog-<你的agent名>.md`:开工写任务书,按节点追加,结束写完成报告(已完成/产出路径/遗留问题/需总控决策事项)。
